# Core hackathon demo: one conversation, three modes

This is the governing acceptance contract for the user's latest demo request (2026-10-14). It supersedes earlier separate Study/Voice layouts, an artificial three-message voice cap and repeated citation terminology. Read this document before implementing the corresponding ingestion, Study or speech work. Update the implementation from these criteria; do not make isolated UI patches without retaining the rules here and in the batch prompts.

## Intended experience

A learner uploads their own document, selects its study sections and enters one consistent conversation with a source-grounded teacher. The same conversation screen has three selectable modes: **Text**, **Voice note**, and **Live voice**. Mode switches preserve the current session, scope, pending answer, conversation transcript and progress. Text entry remains available in every mode. Finished learning, assessments and progress remain server-authoritative.

Study enters ready for text conversation. The Voice shortcut enters Live voice, ready to start a real microphone/audio connection with one clear Start button. A voice-note entry selects record-and-send mode. Support the existing `mode=voice` live-voice entry, `mode=voice-note` for notes and default/`mode=text` for text. A mode is selected by entry context rather than requiring a second manual tab choice. Microphone permission and browser autoplay constraints must be handled through a user start gesture.

The screen presents a teacher message, the learner response and friendly feedback in conversational order. Hide internal grading/rubric/expected-answer details before submission. Confidence is a small understandable 1–5 control, usable alongside typed, recorded or spoken answers. It must be supplied before the server assesses an answer. Live tutoring does not independently complete a title, change the scope or create a grade. A live teacher should acknowledge answers and request confidence/assessment rather than pre-empting the calibrated Reviewer verdict.

## Modes

**Text:** an immediately usable composer, source-based teaching/question and typed answer; pending work has a clear status, not a blank or permanently disabled composer. Send invokes the existing versioned, idempotent answer/Reviewer path.

**Voice note:** explicitly record, stop, preview/edit the transcript and send it through that same answer path. Teacher text can be heard using supported TTS. Recording is distinct from continuous live conversation. Do not retain raw microphone audio by default. Typed fallback is always available.

**Live voice:** genuine bidirectional audio through a verified provider connection, with microphone input, teacher speech output, start/mute/stop and a readable transcript. Use actual OpenAI Realtime WebRTC if supported by the configured provider; do not label manual recording or serial HTTP STT/TTS as live realtime. The server authorizes the owned session/current item and mints only a short-lived client credential through app/llm.py. The browser validates the exact OpenAI calls endpoint, then appends the minted model as a `model` query parameter before submitting SDP; the tested calls endpoint requires this parameter. Never send the permanent API key, hidden expected answer or private rubric to the browser/provider realtime context. Source excerpts and the current public teaching/question ground the conversation. Native realtime dialogue is prompt-grounded; it is not the structured, quote-validated assessment pipeline. Keep that distinction accurate.

If live connection, microphone or speech-provider access fails, show the actual reason with a retry and keep the text/voice-note alternatives usable. This is a failure state, never a fabricated connection success. Stop tracks, peer connections and playback on stop, mode exit or unmount; avoid simultaneous note/live capture. A short demo session can have a clear time limit; client timing is not a server-enforced provider-session lifetime.

## Friendly evidence and useful visuals

Keep original-source provenance and tenant authorization internally. Show a quiet **Source** or **View original** disclosure instead of repeatedly saying “citation” in the main teacher conversation. A learner can still inspect the original quoted evidence and original document/page/section. Do not remove grounding to make the interface friendlier. Never display citation IDs, model JSON or internal role names as conversation copy.

Where the original PDF supports it, an authenticated rendering of its actual page may illustrate the teacher's point. Label it as the original page and preserve the exact page locator. Optional visuals must be genuine source content; do not invent diagrams or substitute generated screenshots. Image previews are subordinate to the core three-mode demo and must not delay PDF intake or communication fixes.

## Done when — key demo gates only

1. **PDF intake works:** a genuine readable text PDF is submitted through the actual multipart API, processed by the durable worker/batches, appears as selectable titled sections, supplies the exact retained original and correct page evidence. A focused regression covers a small PDF and crossing one resumable batch boundary; it must not mock PDF extraction. Corrupt, encrypted or scanned/attention outcomes remain explicit. Fresh Docker images contain the checksum-verified tokenizer data, so PDF processing never depends on manually copying a cache into a running container.
2. **One interface, correct entry modes:** Study/text, voice-note and Voice/live entry each select the intended mode. The learner can switch all three without losing the current session, scope, draft or transcript. The same teacher/answer/confidence/feedback layout and server grading path apply. A focused browser scenario exercises the three entries and state preservation and runs in GitHub CI; retain existing valuable safety/learning checks, do not proliferate superficial tests.
3. **Actual communication is demonstrated:** real typed answer/feedback, note STT plus TTS provider proof where configured, and real realtime credential/connection/audio capability. Deterministic UI/media tests verify states and cleanup; they are not proof of audible live speech. Record exact passed/failed/blocked distinctions. A provider probe never becomes a claim of verified real-human microphone/audibility. Live voice does not bypass confidence or server assessment.
4. **Reviewable delivery:** the governing prompts, API/data/privacy documentation and build state describe the final behavior; code/tests reflect these rules; frozen frontend build and relevant backend/browser gates pass; source is published to main and the existing authorized cloud app is updated. Keep user data/configuration intact. A separate user-machine localhost app is not remotely updated by a cloud deployment.

Focus on these gates under the one-hour demo deadline. Add only tests that protect real PDF/source integrity, the shared entry/mode behavior, owned transient speech and the actual provider path. Keep private documents, credentials, ephemeral tokens and voice content out of tracked evidence. Visible live transcript is retained while the screen is mounted; full transcript reconstruction after reload is not yet implemented. A demo-mode cloud deployment retains its explicit offline badge and cannot be counted as configured live-provider proof.
